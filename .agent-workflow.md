# Agent Workflow Reference

Quick reference for AI-assisted work in mgz-pkmn.

The repository uses an AI Pit Crew pattern as a coordination layer, inspired by [@bobbylough](https://github.com/bobbylough)'s [ai-pit-crew](https://github.com/bobbylough/ai-pit-crew) project:

```text
Human sets direction -> One agent implements -> A different agent reviews -> Human approves
```

The human owns product direction, prioritization, architecture decisions, merge approval, and release timing. Agents contribute focused implementation, tests, verification notes, and cross-review.

## Source Of Truth

mgz-pkmn leans on GitHub itself as the active-work board. There is no separate task file checked into the repo — every piece of state lives where it's most authoritative:

| State | Where it lives |
| --- | --- |
| Backlog and prioritization | GitHub issues + milestones + project board |
| Roadmap navigator | [docs/roadmap.md](docs/roadmap.md) |
| Project invariants and code conventions | [AGENTS.md](AGENTS.md) |
| Branch, PR, CI, and DCO workflow | [CLAUDE.md](CLAUDE.md), [docs/contributing.md](docs/contributing.md) |
| Who's working on what | Open branches on `origin` + the PR's draft / open status |
| Implementation summary | The PR body's What / Why / How to verify |
| Review handoff | PR reviewer field, `@codex` / `@claude` comments |
| Blocked work | `blocked` label on the issue or PR, with a comment naming the blocker |
| Author-agent attribution | `agent:claude` / `agent:codex` / `agent:copilot` label on the PR |

Before starting work, run `gh issue list` and `gh pr list` to see what's already in flight. Don't rely on cached context — branches and PRs are the shared mutable state.

## The Loop

```text
Select -> Claim -> Implement -> Verify -> Review -> Human approval -> Merge
```

### 1. Select

Use a human assignment or a GitHub issue. If selecting work yourself, follow [CLAUDE.md](CLAUDE.md): prefer bugs, small well-scoped changes, and issues aligned with the current milestone. Skip issues labelled `wip`, `blocked`, or `needs-discussion`.

Every code change should be traceable to a GitHub issue unless the human explicitly scopes a docs-only or workflow-only change.

### 2. Claim

The claim is implicit in pushing the branch:

1. `git checkout -b <issueNumber>-<short-description>` per [CLAUDE.md](CLAUDE.md).
2. Push the branch as soon as you have a first commit (or an empty commit + an early draft PR if the work will take more than one session).
3. `gh pr list --search "<issue number>"` is the canonical "is anyone on this?" check. If a branch or PR already references the issue, leave a comment instead of starting parallel work.

### 3. Implement

Follow [AGENTS.md](AGENTS.md):

- Preserve dataclass-driven data shapes across module boundaries.
- Use `spreadsheet.Row` as the canonical pipeline unit.
- Keep pure modules pure and I/O at the edges.
- Match existing source, API, web, and docs patterns.
- Keep changes small and reviewable.
- Add tests before or alongside behavior changes.
- Update docs and changelog entries when public behavior changes.

### 4. Verify

Run the narrowest useful checks while iterating, then the project gate before opening the PR for review:

```bash
make fix
make check
```

If the change touches `web/`, also run:

```bash
cd web && npm run build
```

Docs-only workflow changes do not require the full test suite unless they affect generated docs, examples, or commands.

### 5. Mark Ready For Review

Open the PR (or flip it out of draft) with [CLAUDE.md Step 5](CLAUDE.md) for the metadata details. The PR body is the implementation summary — write the What / Why / How to verify there, not anywhere else. Then:

1. Add an `agent:<name>` label identifying the author agent (`agent:claude`, `agent:codex`, `agent:copilot`).
2. Trigger the cross-agent reviewer (see table below).

Suggested review pairings:

| Author | Reviewer |
| --- | --- |
| Claude | Codex or Copilot |
| Codex | Claude or Copilot |
| Copilot | Claude or Codex |
| Gemini | Codex or Claude |

Reviewer triggers — one of these, matched to the reviewer in the pairing table:

| Reviewer | Trigger |
| --- | --- |
| Codex | `gh pr comment <PR> --body "@codex review"` (chatgpt-codex-connector bot) |
| Copilot | `gh pr edit <PR> --add-reviewer Copilot` (paused via Copilot credits through 2026-07-01) |
| Claude | `gh pr comment <PR> --body "@claude review"` (via [`.github/workflows/claude-review.yml`](.github/workflows/claude-review.yml); see [ADR-0024](docs/adr/0024-claude-review-github-action.md)) |

If a blocker turns up mid-flight, flip the PR to draft, add the `blocked` label, and comment on the PR naming the blocker and who needs to resolve it.

### 6. Review

The reviewing agent should check:

- Correctness against the issue or human request.
- Alignment with [AGENTS.md](AGENTS.md) invariants.
- Edge cases, error handling, and security implications.
- Test coverage and verification notes.
- Documentation and changelog updates where applicable.

If review finds required fixes, the author addresses them in the same PR; the PR state (open with unresolved review threads) is the signal that work isn't done.

### 7. Human Approval

The human makes the final call. Agents do not merge their own work.

For PRs, follow the PR verification artifact rules in [AGENTS.md](AGENTS.md): agents leave the placeholder and local verification notes; the developer attaches screenshots, Jam clips, or external artifacts when required.

## Multi-PR coordination on a single issue

When an issue is sliced into multiple PRs (e.g. parent issue + slice 1 / slice 2 / slice 3), keep the coordination checklist in the parent issue body, not in a separate file. Each slice PR closes its own issue (or references the parent with `Refs #N`), and the parent issue is closed once the last slice merges.
